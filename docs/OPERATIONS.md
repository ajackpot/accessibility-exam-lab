# 검증된 문제 은행 운영 절차

이 문서는 별도 실행자의 재현 가능한 작업 지시입니다. 저장소 밖의 대화·비공개 노트·개인 첨부파일·하드코딩한 인증 토큰에 의존하지 않습니다. 저장소는 `https://github.com/ajackpot/accessibility-exam-lab`입니다. 배포 권한과 실행 비용이 확인된 환경에서만 원격 작업을 수행합니다. 정적 앱이나 CI가 자동으로 AI 사용 권한을 얻지는 않습니다.

## 고정 경계

- 대상: 웹접근성전문가 2급, 2026-05-07 필기·실기 출제기준
- 필기: 표준·인터넷·HTML·CSS/스크립트·정보접근성 5과목, 정규 모의 구성은 20문항씩/총100/5지선다/150분
- 실기: 구현(미완성 소스 완성)과 점검(위반 지적·이유·개선), KWCAG2.2 네 원칙. 앱의 점수는 독자적인 변형 연습 배점이며 공식 실기 배점 아님
- 우선 출처: 시험기관 공식 안내, 해당 출제기준, KWCAG2.2, 날짜가 고정된 HTML5.2, WAI-ARIA1.2, CSS2.2(초안임을 표시), 현행 법령. 공식 안내 시작점: http://www.ualab.or.kr/license.html
- 오래된 KWCAG2.1 무정답 샘플을 최신 정답 근거로 재사용하지 않음. 법률은 현재 시행 조문·시행일과 과거 출제기준 충돌을 반드시 확인하고 해소할 수 없는 충돌은 즉시 탈락
- 국제 표준의 상세 성공기준을 2급 필기 핵심 범위로 무차별 확장하지 않음. HTML Living Standard와 시험의 고정 HTML5.2판을 구분
- 원본 공식 샘플·첨부문서·유료 문제집은 복제하지 않음. 독자 지문/예제 코드와 필요한 짧은 근거 요약·링크만 포함
- 기존 시드는 계속 testOnly. 2026-10-02부터 정규 은행을 즉시 확대하며 첫날 시드 전용 제한은 대체됨. 새 검증 문항만 testOnly=false로 작성. 합성 테스트 문항·새로운 보기 조합을 새 학습 문항 수에 포함하지 않음

## 2. 근거 카드 → 문항 → 독립 검토

각 작은 묶음에 다음 단계를 별도 역할로 수행합니다. 한 모델의 동의만으로 검증 완료로 하지 않습니다.

1. 조사: 1차 자료 원문을 열어 학습 목표, 판/시행일, 정확한 절, 조건·예외와 확인일을 기록합니다. 법령/ARIA/특정 브라우저 동작은 기억으로 확정하지 않습니다
2. 출제: 지문과 독립 코드를 만들고 모든 정답·오답에 이유와 근거를 연결합니다. 공유 선택지는 기본 정의와 필요한 문맥별 추가 이유만 분리합니다. 전용 선택지의 이유를 두 필드에 반복하지 않습니다
3. 독립 풀이: 정답 키/해설을 가린 질문·조건·보기만 다른 검토자에게 제공하여 답과 이유를 받습니다
4. 기준 검증: 키와 독립 답을 비교하고 원문에서 정답과 모든 오답의 판정을 확인합니다. 복수 정답/정답 없음/조건 누락 반례를 찾습니다
5. 접근성 검토: 색·이미지·공간 관계에 의존한 질문에 동등한 텍스트 조건이 있는지, 그 조건이 정답을 노출하지 않는지 확인합니다. 코드 전체를 라디오 레이블마다 반복하지 않습니다
6. 최초 검토와 수정 검토 두 번을 합쳐 후보당 최대 3회입니다. 시작한 검토를 1회로 세고, 매회 3~5단계와 문안·구조 검사를 다시 수행합니다. 출제자와 맹검 풀이자는 달라야 하고 이전 정답을 본 검토자는 수정본의 새 맹검을 맡지 않습니다. 모든 필수 검사를 같은 개정판에서 통과해야 accepted입니다. 해소할 수 없는 근거 충돌·단일 정답 불명·범위·권리 문제는 즉시 rejected입니다. 수정 가능한 문안·조건·구조만 남은 횟수 안에서 revise로 처리하고, 3회 미통과 또는 회차 판정 마감까지 미완료면 rejected로 종결합니다. not_run을 통과로 기록하지 않습니다
7. 통과한 것만 `reviewNote`, 출처, 안정 ID/개정판, `testOnly:false`, `verificationStatus:'published'`로 새 묶음에 추가합니다. 기존 testOnly 항목을 조용히 학습용으로 재분류하지 않습니다

수량은 목표이지 보장량이 아닙니다. 1회차의 필기 50개(과목별 10개)·실기 8개 후보 계획을 후속 회차의 상한으로 유지하며, 매 회차 실제 목표는 직전 공백·근거·검토 여력에 따라 그보다 적게 정할 수 있습니다. 첫 누적 목표는 5과목별 20개, 총 100개의 정규 고유 templateId입니다. 5지선다 출제 조건까지 충족해야 모의시험을 엽니다. 좋은 새 문항이 없으면 배포를 건너뜁니다. 후보 수·채택 수·보기 조합 수를 공개 문항 수로 보고하지 않습니다.

회차 종료에는 모든 후보를 accepted 또는 rejected로 결정하고 pending/revise는 0개로 만듭니다. 후보 ID·revision·templateId·다음 회차로 횟수를 초기화하지 않습니다. 같은 학습 목표의 재개방은 이번 campaign에서 최대 1회이며, 기존 탈락 원인을 해결하는 새로운 1차 근거를 직접 확인해야 합니다. 기존 회차·후보·판정·횟수·근거를 연결하고 재개방 최대 3회, 계보 전체 최대 6회를 지킵니다. 같은 문서 재독·표현 수정·모델의 재동의는 새 근거가 아닙니다. 자세한 계약은 PRD 13.6과 DATA-CONTRACT를 따릅니다.

매 회차 `docs/rounds/<roundId>.json`과 `.md`를 작성합니다. JSON Schema와 교차 필드 조건을 검사하고 채택·탈락·검토 횟수·사유·1차 근거·실제 공개 수를 기록합니다. 다음 회차가 보완할 과목별 범위 공백, 필요한 원문·예외·반례, 논리적 불확실성, 다음 행동·완료 조건은 필수입니다. 공백이 없으면 확인 범위와 이유를 씁니다. 내부 사고 과정·원시 작업 로그·개인 첨부는 공개하지 않습니다. 판정 종료 시각은 `closedAt`이며 공개 확인은 그 뒤에 완료될 수 있지만 최종 동결과 다음 운영 계획을 지켜야 합니다. 탈락 후보는 판정 마감 뒤에 재개방하지 않습니다.

앱 코드를 고칠 때는 APP_VERSION과 package.json/lockfile의 버전을 함께 올리고, index.html의 app.js/CSS URL, src/app.js·domain.js·legacy-materials.js·legacy-question-display.js·workflows.js·storage.js·backup.js의 내부 모듈 import, QA harness/fixture/viewport의 진입·모듈 query 버전을 일치시킵니다. 버전 URL은 새 페이지가 오래된 캐시 모듈과 섞이는 것을 방지하기 위한 정상 릴리스 절차입니다. 바닥글의 실제 runtime 버전과 수정된 동작을 모두 확인해야 공개 검증 완료입니다.

### 2.1 문항 등록 시 간결한 지문·참고 사항·보기 함께 작성

보기 자료가 있으면 문항 내용도 해당 자료에 맞춰 작성해야 합니다. 보기는 문제 바로 아래에서 분석할 지문·이미지·그래프·수식·코드이며 답으로 고르는 선택지와 다릅니다. 현재 지원되는 자료는 코드 텍스트이고, 다른 유형을 추가할 때도 같은 계약을 적용할 렌더러·접근성 검증이 필요합니다.

1. 자료의 목적을 question/explanation으로 분류합니다. 필수 분석 자료만 보기로 만들고 완성 답안·해설 예시는 공개 시점까지 분리합니다
2. 지문에 ‘다음 보기의 코드를 읽고, p 요소에 적용되는 color 값을 고르시오.’처럼 **자료 유형·대상·풀이 행동**을 1~2문장 지문에 통합합니다. 가정·제약·입력 형식은 `notes`로 분리하고 불필요한 참고 사항 영역은 만들지 않습니다. 조건만 쓰거나 `instruction` 메타데이터에만 넣으면 안 됩니다. 여러 파일은 각각 파일명을 지칭합니다
3. 필수 자료를 없애면 풀 수 없는지, 실제 제공한 내용과 문장의 대상·행동이 맞는지 독립 검토합니다. 없는데 있다고 한 자료, 불필요한 자료, 답 유도 제목·완성 코드, 선택지와 보기의 혼동은 등록·공개를 막습니다
4. `validateBankForPublication` 기반 validate/build/check로 구조를 검사합니다. exact stem 포함만으로 통과시키지 않으며 빈 코드·보기/코드/풀이 동작 누락·자료 없는 코드 참조·모호한 여러 파일명, 장문 지문·중복 참고 사항을 거부합니다. 정규식 통과는 의미 검토를 대체하지 않습니다
5. 전 문항의 실제 DOM을 **핵심 지문 → 필요한 참고 사항 → 박스형 보기 → 선택지/실기 답안**으로 읽고, 모바일 폭에서도 순서와 코드 도구가 유지되는지 확인합니다. 보기 없는 문항에 빈 박스를 만들지 않습니다. 시간제·채점 전·종료 후 해설 모드의 누출 회귀도 수행합니다
6. 결과를 reviewNote와 회차 대장에 기록합니다. 불합격 문항은 최대 3회·회차 마감 안에서만 수정하고 이후 탈락으로 종결합니다. 미통과 후보를 출제 가능한 등록 상태나 공개 상태로 승격하지 않습니다. 본 절의 등록은 콘텐츠 제작 절차이며 앱에 편집·등록 UI가 있다는 의미가 아닙니다

### 2.2 AI 요청문과 과거 원문 확인

- 생성 요청은 역할·평가·설명·불확실성만 짧은 대화체로 씁니다. 개인정보·붙여넣기·복사·다운로드 안내는 앱 UI에 두고 새 문항의 서술 과제 데이터에도 섞지 않습니다
- 과거 학습 화면의 간결한 표시와 AI 원문 내보내기를 구분합니다. 정확히 알려진 과거 스냅샷만 표시를 개선하며 저장 원문·답·점수·해시는 수정하지 않습니다
- 문항·참고 사항·코드·서술 과제·사용자 답안 원문이 한 글자도 유실되지 않는지 검사합니다. 구판 데이터에 있던 앱 안내는 원문 보존 예외입니다
- 독립 모드의 키/루브릭/해설 제외, 비교 모드 공개 시점, 시간제 차단, 빈 답안 제외, 서술형/앱 배점 분리와 미작성 처리를 함께 회귀합니다

### 2.3 정규 은행 전환의 앱 회귀

현재 대상 앱은 0.2.7이며 출제기 버전 2와 은행 schemaVersion 3은 유지합니다. 새 정규 문항을 시드와 함께 누적할 때 다음을 검사합니다.

- 홈·조건 지정·같은 범위 재시작은 현재 유형·과목·과제군·선택지 수·출제 범위·이력에 맞는 정규 문항이 있으면 정규 문항만 출제합니다. 부족분을 테스트로 채우지 않습니다
- 정규 문항이 0개일 때만 테스트 전용임을 분명히 안내하여 시드를 사용합니다. 후보 0개·직접 입력한 수량 초과는 안전하게 거절하고, 기본 빠른 시작 수와 요약은 실제 가능 수와 일치합니다
- 명시적 과거 오답 복습은 테스트/혼합 목표도 유지합니다. 기존 이어하기·기록·백업·시간 전환에서 원문·선택지 순서·답안·점수·스냅샷을 바꾸지 않습니다
- 혼합 세션의 홈·기록·시작 대기·결과는 정규와 테스트의 실제 수를 표시합니다. 세트 전체 점수와 문항별 정규/테스트 통계 분리 설명을 확인합니다
- 정규 100문항 모의시험은 여전히 5과목 각각 20개의 정규 고유 templateId와 5지선다 조건을 충족해야 합니다

### 2.4 선택지 해설 저작·반복 방지 (PRD 1.8)

1. 모든 문항의 question.explanation에는 전체 풀이를 씁니다. 필수 option.explanation에는 전용 선택지의 문항별 이유 또는 공유 선택지의 정의·판단 이유를 한 번 작성합니다. 링크의 contextExplanation에는 이 기본 설명에 없는 실제 적용 조건·예외·추가 이유만 필요한 때 쓰며, 없으면 생략하거나 빈 문자열을 둡니다
2. 두 필드를 채우려고 복사하거나 ‘정답이다./오답이다.’만 덧붙이지 않습니다. 단어만 바꾼 같은 의미, 내용 없는 ‘이 문항에 맞다’ 반복, 선택지 이유 전체를 문항 해설에 다시 복제하는 패턴도 독립 문안 검토에서 거부합니다. 정오 역할·부정·범위·값·코드의 차이는 보존합니다
3. 원문 근거 확인과 맹검 풀이 이후, 각 선택지의 두 설명을 나란히 읽어 ‘기본 정의’, ‘새 문맥 정보’, ‘중복/불필요’로 판정합니다. 필요한 정보가 없는 쪽만 비우거나 해당 문항의 한 설명으로 정리하며 정답과 근거를 바꾸지 않습니다. 새 지식·수정 조건을 덧붙여 해설을 억지로 다르게 만들지 않습니다
4. **현재 확인된 manifest를 교체하기 전에** 후보 JSON 경로를 명시한 validate/build를 실행합니다. 고정 경로·SHA-256으로 검증한 과거 regular.1(없으면 seed.4)과 정확히 같은 문항·연결 선택지만 기존 예외로 유지하고, 새/변경 필기 문항에는 엄격한 해설 검사를 수행합니다. 인자 없는 check/build와 릴리스 대장 검사도 같은 저작 경계를 검사하므로 후보 manifest를 먼저 설치해도 우회되지 않습니다. 기준 파일이 없으면 예외가 없고 손상됐으면 실패하며, 후보에 맞춰 과거 파일·해시 상수를 바꾸지 않습니다
5. 자동 검사는 정오 문구 외 실제 근거가 있는 기본 해설, 정확/인용·코드 구간 밖 공백 중복, 역할 일치 정오 선행 문장, 정오 문장만 있는 보충 해설, 공통 완전 문장의 경계 중복을 검사합니다. 의미만 같은 재진술은 사람의 문안 검토가 담당합니다. 줄바꿈·탭·슬래시가 있으면 내부 공백 전체를 유지하는 안전 경계와 필수 설명 누락·새 문맥 손실·반대 역할·코드/인용 내부 공백·Unicode·true/false 차이가 없는지 함께 회귀하며 기존 저장·백업·점수·순서·해시는 유지합니다
6. 1.7의 후보당 최대 3회 검토와 회차 판정 마감을 그대로 적용합니다. 기존 종결 후보의 검토 횟수·판정을 해설 표시 수정 때문에 다시 쓰지 않습니다. 이후 모든 회차의 새 author 작업 지시에는 이 절을 전달하며 과거의 ‘모든 contextExplanation 비어 있지 않게 작성’ 지시를 재사용하지 않습니다

2026-10-02 regular.1의 활성 필기 연결 300개 전수 대조 결과: 정확/공백 중복 140개, 역할에 맞는 정오 문장만 덧붙인 중복 50개, 공통 완전 문장에 새 맥락을 더한 문자열 패턴 0개, 문자열이 다른 쌍 110개였습니다. 정확 중복은 테스트 시드 40개와 정규 표준·정보접근성 100개, 정오 선행 중복은 정규 CSS/스크립트 50개입니다. 110개를 추가 문안 검토해 실제 기본 정의+새 맥락 91개, 같은 뜻/빈 판정의 재진술 15개, IPv6 오답의 비정보성 기본 문구 4개로 구별했습니다. 뒤의 세 분류는 내용 검토 결과이며 의미 유사도 알고리즘의 판정이 아닙니다. 시드 seed.1~seed.4는 각각 정확 중복 40개와 다른 쌍 10개가 있습니다.

재발 원인은 표시 함수의 전체 문자열 비교만으로는 ‘오답이다. ’가 붙은 같은 설명을 찾지 못한 점과, 기존 필드 검증·과거 작성 계약이 필요 없는 문맥 해설까지 요구한 점입니다. 0.2.8은 표시의 보수적 정확 비교와 검토된 19개 원문 예외, 새 문항의 선택적 문맥·발행 검사·문안 검토를 함께 사용합니다. 19개 예외는 원래 문항·선택지 전체가 정확히 보존된 후속 schemaVersion 3 누적본에도 이어집니다. 다음 회차의 은행 버전이 바뀌었다는 이유로 반복 표시가 되살아나지 않으며, 변경된 원본에는 적용하지 않습니다. 확인되지 않은 생성 스크립트나 자연어 전체의 자동 중복 판별을 주장하지 않습니다.

### 2.5 정답을 포함한 모든 선택지의 문안 검토 (PRD 1.9)

1. 필기 전용·공유와 실기 single/multi 전체의 지문·조건·보기·선택지를 한 세트로 검토합니다. 오답마다 같은 학습 목표의 개념 혼동·적용 착오와 이 조건에서 틀리는 근거를 짧게 기록합니다. 실제 이용 통계가 없으면 ‘흔한 실수’는 검토한 오개념 가설이지 관찰 사실이 아닙니다
2. 정답과 오답의 문법·관점·시제·구체성·정보량을 나란히 확인합니다. 정답만 길고 포괄적인 해결책, 오답만 극단적 부정·배타 표현, 지문 단어와 정답의 눈에 띄는 반복, 서로 포함되는 답을 찾습니다. 무관한 기능·상식적으로 터무니없는 주장 대신 실제로 혼동 가능한 대안을 사용합니다
3. ‘만·항상·절대·반드시·모든·전혀’ 등의 탐지 결과는 검토 후보로 취급합니다. 필요한 범위·예외·수량·집합·표준 요구와 코드 연산자를 함께 확인하고 유지 이유를 남깁니다. 검색 0건은 통과가 아니며 발견 즉시 치환하거나 제한어 없는 문장을 자동 승인하지 않습니다. 정답에 같은 단어를 억지로 더하는 방식도 사용하지 않습니다
4. 한정어를 지우거나 표현을 완화한 뒤에는 모든 선택지가 동시에 참이 되는 조건과 새로운 유효 대안을 찾습니다. 문항의 원래 학습 목표·조건·정답 의미를 유지할 수 없으면 편집 정정으로 통과시키지 않습니다. 새 맹검 풀이와 1차 근거 확인은 생략할 수 없습니다
5. `authoringAccessibility`의 짧은 결론에 오개념 타당성·평행성·표현 단서·필수 조건 보존을 포함합니다. 자동 탐지와 독립 내용 판정을 분리하고 다섯 gate·엄격한 해설 저작 검사·유한 검토 한도를 같은 개정판에 적용합니다. 출제기 섞기·schemaVersion 3·0.2.8의 해설 표시 규칙은 이 문안 검토로 대체하지 않습니다

### 2.6 실기 항목 사이의 답안 노출과 입력 형식

실기 전체의 채점 전 화면을 한 묶음으로 검사합니다. 뒤 항목의 미채점 선택지·예문이 앞선 빈칸의 완성 답이나 유일한 정답 조합을 직접 노출하면 문안 gate에서 실패합니다. 필요한 보기·환경 조건, 공통 용어와 여러 후보 간의 관계는 유지하며 단어 탐지로 자동 삭제하지 않습니다. 고정 답안의 리터럴 형식·인코딩·대소문자 제약은 풀이 전에 명시하고 실제 답 문자열을 미리 쓰지 않습니다. 실제 채점 함수가 동등 표기를 거부하는지 조건과 함께 대조합니다.

2회차의 건너뛰기 링크 후보는 세 번째 검토에서 교차 답안 노출이 남아 탈락했습니다. 판정과3회 이력을 보존하고 네 번째 검토·새 ID 등록·다음 회차의 단순 문구 수정으로 우회하지 않습니다. 다음 회차는 이 결함 유형을 최초 작성과 독립 검토에 포함합니다. 자세한 근거와 비차단 주의사항은 round-002 대장·보고서에 있습니다.

### 2.7 시간 기본값과 사용자 입력 보존 회귀 (0.2.9)

- 새 필기 설정에서 전체·100문항 모의시험은150분, 단일 과목은30분을 사용합니다. 무제한 상태에서 범위를 바꾸고 나중에 시간제로 전환해도 같은 기준입니다. 실기 짧은 연습30분은 그대로입니다
- 제한 시간을 직접 입력한 뒤에는 값이30·150처럼 기본값과 같아도 보호합니다. 범위·구성·시간 방식을 바꾸거나 브라우저 뒤로/앞으로 복원해도90분 등 사용자 값과 비어 있는 입력을 기본값으로 덮지 않습니다. 유효하지 않은 시간은 시간제 시작을 차단합니다
- 기존 config를 받아 여는 설정, 같은 범위 재시도와 저장된 세션의 시간·마감 시각·답안·순서·백업은 보존합니다. 새 편집 의도 정보는 화면/경로에만 두고 학습 기록 스키마에 저장하지 않습니다
- 실제100문항 구성, 시간제 시작/새로고침/제출/결과, 과목과 전체 전환, 명시적30·90·150, 시작 실패 및 오래된 세션을 회귀합니다. 이미 시작한 짧은 타이머를 자동으로150분으로 늘리지 않습니다

## 3. 불변 릴리스 만들기

`docs/DATA-CONTRACT.md`를 준수합니다. 기존 릴리스 파일을 덮어쓰지 않고 새 bankVersion을 부여합니다. 이전 모든 immutable release를 보존합니다.

```sh
npm ci
node scripts/validate-bank.mjs /path/to/reviewed-bank.json
node scripts/build.mjs /path/to/reviewed-bank.json
npm run check
npm test
```

`npm run build`는 현재 manifest가 가리키는 활성 불변 은행을 다시 검사·빌드하는 명령으로 유지합니다. 과거 시드로 되돌리는 기본값을 사용하지 않습니다. 기존 `data/seed-bank.json`·`data/seed-bank-v2.json`·`data/seed-bank-v3.json`과 `seed.1`·`seed.2`·`seed.3` 불변 릴리스는 보존합니다. 후속 릴리스에서는 새 파일 경로를 build에 명시하세요. scripts/check는 현재 manifest의 실제 릴리스를 검사하며, seed 회귀는 기존 시드 파일을 별도로 유지합니다. 빌드는 불변 버전 경로가 이미 다른 바이트로 존재하면 거부합니다.

### 4.4 Git 권한 10분 종료와 미확정 결과의 유한 재대조

1. Git 제공자의 실제 승인 요청 알림이 도착했을 때 원래 콘텐츠 roundId·별도 executionId·알림 시각·10분 뒤 deadline을 작업 상태에 기록합니다. 작업/네트워크 호출 시작 시각으로 추측하지 않습니다. `startGitPermissionWait`/`advanceGitPermissionWait`는 최대 1초의 다음 대기 구간을 계산하는 순수 도우미이며 스스로 기다리거나 승인하지 않습니다. 실행자는 짧은 도구 yield/대기로 부모 대화를 응답 가능하게 유지합니다. Library의 업로드 권한 대기는 Git 권한 타이머로 처리하지 않습니다. 명시적 거부는 시간 초과로 꾸미거나 우회하지 않습니다
2. 응답을 확인하기 전에 10분이 되면 `download_only` 상태와 중단 시각을 **추가 쓰기 전에 지속 저장**하고 해당 회차의 모든 후속 blob/tree/commit/ref 쓰기·재시도·강제 갱신을 멈춥니다. 늦은 승인이나 같은 회차 재호출도 이 상태를 되돌리지 않습니다. 대기 요청 식별자는 비공개 작업 상태에만 둡니다. 지원되는 pending elicitation 취소 도구가 있으면 정확한 요청을 취소하되, `cancelled`/`already_resolved`/`expired`/불확실 응답을 각각 기록합니다. 요청 취소는 실제 Git 작업 취소 증거가 아닙니다
3. 원격 head·예상 commit·생성 객체를 읽기 전용으로 재확인합니다. 진행/결과 불명인 ref 호출은 head가 잠깐 기준 커밋과 같더라도 `unknown`입니다. 제출하지 않았거나 확실히 실패한 ref이고 head도 같을 때만 ref 미변경입니다. 예상 commit이 이미 head면 `applied`로 보고하며 Git 미변경이라고 말하지 않습니다. 객체 생성 여부와 ref 상태를 분리합니다. ref에 연결되지 않은 blob의 생성 여부가 불명인 것은 ref 갱신 불명을 뜻하지 않습니다. 그 동일 객체 쓰기는 중복하지 않고, 실제 제출된 ref 갱신이 불명일 때만 그와 충돌할 동기화/공개를 제한합니다. 불확실한 쓰기는 반복하지 않으며 요청 취소를 확인하려고 새 Git 쓰기를 만들지 않습니다
4. 확인한 기준 커밋의 공개 파일 export와 전체 경로·SHA-256 목록을 보관합니다. 후보 공개 허용 목록의 변경·추가·삭제 파일을 의미/개인정보 검토하고 정확한 최종 SHA-256을 고정합니다. 원격 export 대신 후보 작업 디렉터리에서 기준 해시를 만들어서는 안 됩니다. 이전 불변 bank·seed를 변경하거나 삭제하지 않습니다. `PUBLICATION-MANIFEST.txt`에 없는 파일, 심볼릭 링크, 경로 탈출·대소문자 충돌·Windows 특수 경로는 거부합니다. 허용 목록과 자동 검사는 내용의 비밀/개인정보 검토를 대체하지 않습니다
5. 비공개 plan JSON에는 전체 공개 파일의 검토 해시·크기 목록 `reviewedFullInventory:[{path,sha256,bytes}]`와 `baseRoot`, `workRoot`, `baseCommit`, `baseVerifiedAt`, `baseInventory:[{path,sha256}]`, `reviewedSha256:{경로:최종해시 또는 삭제시 null}`, 시간 초과 `wait`, 읽기 전용 `gitOutcome`, 선택적 `parentDeliverySha256`와 그에 대응하는 `parentManifest`를 넣습니다. 이 JSON 계획과 `node scripts/download-fallback.mjs PRIVATE-PLAN.json DELTA.zip COMPLETE.zip` CLI는 실제 권한 timeout에 따른 v1 묶음 전용입니다. v2 오프라인 후속 묶음은 로컬 JavaScript에서 `freezePublicDelta`와 `writeOfflineDeliveryPair`를 호출하고, 검증된 영수증과 실제 `Map`인 manifests·ledgers·banks, 원격 inventory와 선행 delta를 순서대로 접은 누적 inventory를 전달합니다. JSON CLI는 Map을 복원하지 않으므로 v2 continuation을 JSON 계획으로 넘기지 않습니다. 두 경로 모두 실제 현재 시각을 사용하며 Git/네트워크/Library 호출 없이 `prepared_not_delivered` 단계까지만 준비합니다. plan·로컬 경로·승인 식별자는 공개 ZIP에 넣지 않습니다. 출력 ZIP은 기존 파일을 덮어쓰지 않습니다
6. 변경분 ZIP에는 `files/` 아래 변경·추가 파일만 원래 상대 경로로 넣고, 기계 판독 `manifest.json`과 `APPLY-KO.txt`를 포함합니다. manifest에는 기준 커밋, 각 before/after 해시·크기, 삭제 경로/기준 해시, Git 불확실성, `deliveryMode:download_only`, `newlyPublishedRegular:0`을 기록합니다. 삭제는 자동 실행하지 않습니다. 앱 학습 기록 가져오기 파일이 아니며 원래 답안·세션·점수·스냅샷·시드/과거 은행은 보존합니다. 수정된 원문을 동결 뒤 새로 만들거나 최종 cutoff를 우회해 ZIP을 생성하지 않습니다. 이미 고정된 ZIP의 재다운로드는 새 콘텐츠 공개가 아닙니다
7. 변경분과 별도 전체본을 각각 검증하고, 두 파일의 지원되는 Library 업로드와 사용자 첨부 전송이 실제 성공한 뒤에만 `delivered`라고 기록합니다. 업로드/첨부가 실패하면 `delivery_failed`로 보고하고 비공개 서명 URL을 우회 전달하지 않습니다. 다운로드 가능 파일 제공과 Git/Pages 공개를 구별하며 새 공개 수는 0입니다. 준비 시 `prepared`, 전달 성공/실패 때 별도의 append-only 영수증 사건을 기록하고 이전 사건/후보를 덮어쓰지 않습니다. 같은 artifact의 최신 상태 사건 하나를 사슬 검사에 넣고 모든 사건 이력은 보존합니다
8. 영수증은 `docs/deliveries/`의 공개용 짧은 결과만 다음 허용된 저장소 반영 때 포함합니다. 전달 직후 해당 회차 Git 쓰기로 기록하지 않습니다. 원격 밖에서도 정확한 ZIP/manifest/영수증/종결 후보·은행 바이트를 복구 가능한 저장소에 보존합니다. 파일 경로만 저장하거나 임시 파일이 남을 것으로 가정하지 않습니다. 서비스 접근 식별자·비공개 링크는 공개 영수증에서 제외합니다

**전체 적용본 필수 동반 (packaging-policy-001):** 새 다운로드 전달은 `writeOfflineDeliveryPair`로 변경분과 전체본을 함께 준비합니다. 전체본 `project/`에는 정확한 공개 허용 목록 전체를 넣고 별도 `manifest.json`·`APPLY-KO.txt`를 제공합니다. 전체본에는 이전 ZIP이 필요하지 않습니다. 원 delta/사슬 해시는 출처 검증용으로만 남깁니다. 모든 파일을 사전에 의미/개인정보 검토하고 검토 inventory와 정확히 대조하며, 원본과 별도 동결한 바이트로 ZIP을 만듭니다. 빈 폴더에 풀고 `project/`에서 build·소스·전체 테스트·발행 검사를 실행합니다. 기본/명시 입력이 동일한 경우의 중복 실행 통합과, 종결 소스 증거를 재사용하는 대체 경로는 아래 validation-efficiency-001의 모든 조건을 충족할 때만 적용합니다. 재사용을 archive 내 실제 전체 테스트 실행으로 보고하지 않습니다. CRC·모든 파일 해시·안전 경로·중복/대소문자 충돌·허용 목록 일치도 확인합니다.

이미 전달된 변경분에 전체본만 추가 제공하는 경우 기존 delta/영수증은 바꾸거나 재첨부하지 않습니다. 정확한 frozenSourceInventory와 별도 packagingRevision의 경로/before/after 해시를 넣어 `freezeCompleteProject`/`writeCompleteZip`으로 생성하고 독립 검토합니다. full 영수증은 `kind:complete_project_delivery`로 원 delta 사슬과 분리하며 업로드·첨부 성공 전에는 prepared입니다. 다음 회차는 기존 delta 사슬의 정확한 기준을 유지하며 전체본에만 추가된 지원 파일도 다음 delta 검토에 빠짐없이 포함합니다.

한국어 안내는 새 빈 폴더 추출, `project/`를 프로젝트 루트로 사용, 기존 프로젝트와 학습 기록 백업, 같은 사이트 주소에서 공개 파일만 교체, 자체 수정 충돌 확인을 포함합니다. `.git`·개인 기록·관련 없는 사용자 파일/서버 설정을 덮어쓰거나 삭제하지 않습니다. 브라우저 저장소는 프로토콜·호스트·포트에 따라 다르므로 주소 변경 시 앱 백업으로 보존/복원합니다. 전체본을 사용한 뒤 같은 회차 delta를 다시 적용하지 않고, ZIP을 앱의 학습 기록 가져오기에 넣지 않습니다. 다운로드 전달은 Git/Pages 공개 완료가 아닙니다.

**공개 완료 뒤 보고서 마감 쓰기:** 콘텐츠와 Pages가 이미 확인됐어도 README·VALIDATION·원래 대장의 공개 확인 기록을 저장하는 후속 Git 쓰기에 권한 지연이 생길 수 있습니다. 이때 변경분은 `deliveryScope:reporting_only`로 변경된 보고 파일만 담고 불변 은행을 다시 넣지 않습니다. 함께 제공하는 전체본에는 완전한 프로젝트를 담습니다. 기준 원격에 같은 은행/해시가 있어야 하며 후보 판정·revision·검토 이력은 정확히 같아야 합니다. 이미 검증된 publication·실제 공개 수는 그대로 유지하고 전달 영수증의 `newlyPublishedRegular:0`만 새 공개가 없음을 뜻합니다. 원래 콘텐츠 공개를 download_only로 소급 분류하지 않습니다. 도우미는 baselineLedgerSha256·은행/commit/확인 시각·불변 판정 부분 해시를 reportingEvidence로 대조합니다. 파일 적용/원격 증거와 기존 전체 대장 검사를 대신하지 않습니다.

**묶음별 최대 10분 재대조:** `startReconciliationWait`/`advanceReconciliationWait`로 artifactSha256별 최초 지속 기록된 `firstUnresolvedAt`과 고정 `deadlineAt`을 관리합니다. 시작 근거는 이미 보관된 읽기 전용 Git 관찰 중 최초 미확정 시각이며 작업/재호출 시작으로 대체하지 않습니다. round-006의 기존 manifest.gitOutcome.observedAt인 2026-10-04T01:27:54.486Z가 그 최초 근거이면 deadlineAt은 01:37:54.486Z입니다. 새 executionId·회차·head 관찰·늦은 승인으로 시계를 재설정하지 않습니다. 실제 권한 알림부터의 10분 대기는 별개로 보존하며 서로 연장하지 않습니다. 기한에 도달하면 해당 Git 단계의 건너뜀을 지속 기록하고 기다리기를 끝냅니다. `unknown` 또는 이미 확인된 적용 증거는 그대로 남기고 이를 해결·실패·미변경으로 바꾸지 않습니다. 결과가 불명인 동안 그 쓰기를 재제출하지 않습니다.

### 새 명시 요청에 따른 단일 blob 재제출의 좁은 예외

미확정 쓰기의 자동 재시도 금지는 기본값이다. 다만 이전 실행이 영구 `download_only`로 끝났고 tree/commit/ref를 전혀 제출하지 않은 분리된 `create_blob`만, **종료 뒤 사용자가 새로 명시한 요청**에 대해 새 executionId로 독립 검토한다. 기존 로컬 실행의 종료와 대기 중인 후속 Git 쓰기가 없음도 독립 확인한다. 원래 저장소·도구·인코딩·해독 바이트·바이트 수·SHA-256·Git blob SHA가 모두 같아야 한다. 60초 이내의 실제 원격 head와 로컬/원격 영구 동결 상태, 별도 신규 권한 대기의 10분 상한·현재 실제 시각·최종 cutoff·전체 발행 검사를 확인한다.


권한 알림 없이 결과가 미확정인 분리된 blob도, 원래 재대조 10분 경과·영구 쓰기 중단·실제 로컬 실행 종료 및 후속 Git 쓰기 대기 없음이 독립 확인되고 종료 후 새로운 명시적 사용자 요청이 있는 경우에만 같은 단일 재제출 guard를 사용한다. 이 경로는 원 `permissionWait:null`과 실제 `no_request_observed` terminal/제출 원문·해시·microsecond UTC 시각을 그대로 결박한다. `download_only`·권한 알림·서버 취소를 만들어 내지 않으며 원 unknown·최초 시계·중단은 유지한다. 동일 저장소·도구·인코딩·해독 바이트·SHA, 새 execution/operation, 실제 fresh head·양쪽 동결·cutoff와 제출 전 하나의 고정된 durable request/object claim 조건은 같다. 원문 해시나 caller Boolean만으로 외부 사실·권한이 인증되는 것은 아니며 운영자가 원 증거와 새 요청을 독립 확인한다. 후속 tree/commit/ref가 제출됐거나 불명인 경로는 허용하지 않는다.

`scripts/blob-retry.mjs`의 `initializeBlobRetryJournal`/`reserveBlobRetry`로 원래 작업당 하나의 고정된 비공개 지속 기록에 요청/객체당 한 번을 **제출 전에** 배타 생성·동기화한다. 실패·불명·중단도 한 번을 소비하며 기록의 이동·삭제·재초기화로 횟수를 되찾지 않는다. 기존 unknown·최초 10분 시계·종결 상태는 그대로 둔다. 증거/지속 기록 누락이나 손상은 차단한다. 자동/예약/늦은 승인·인코딩 변경·tree-inline 우회·tree/commit/ref 재시도는 허용하지 않으며 이 검사는 공개 승인이나 배포 완료를 뜻하지 않는다.


**후속 회차의 누적성:** 시작 전에 최신 원격 manifest와 전체 전달 영수증을 함께 대조합니다. `validateDeliveryChain`은 누락/분기/중복·원문 해시·accepted 목표를 확인하는 보조 검사입니다. 미해결 항목 수만으로 모든 후속 콘텐츠를 막지 않습니다. 재대조 상한 뒤에는 `validateOfflineContinuation`으로 아래 조건을 확인하고 새 조사 및 정규 일정의 오프라인 누적 회차를 이어 갑니다. 검증이 실패하면 실패한 계보/데이터를 고치기 전 누적본 작성·전달을 진행하지 않되 독립적인 근거 조사는 계속할 수 있습니다.

1. 첫 오프라인 선행자는 정확히 전달 확인된 round-006입니다. ZIP·manifest·영수증·종결 대장·은행 원문을 다시 읽어 artifact/manifest/ledger/bank SHA-256과 전달 상태를 대조합니다. 그 뒤는 검증된 최신 전달 선행자 한 갈래만 따릅니다. 누락된 선행자·다른 바이트·분기·전달 실패를 전달 성공으로 간주하지 않습니다
2. `docs/deliveries/offline-chain.json`에 공개 가능한 영수증·manifest와 불변 원본 대장의 ledgerPaths를 연결합니다. 각 회차의 ZIP, 종결 대장, 은행 및 해시를 복구 가능한 불변 체크포인트로 보존합니다. accepted 목표·bankVersion·시작한 검토 횟수는 미해결/미전달 상태에서도 예약하며 새 ID·재검토·새 실행으로 초기화하지 않습니다
3. 후속 대장의 `baseline.sourceCommit`은 실제 확인된 원격 anchor를 유지하고 `baseline.bankVersion`/`bankSha256`는 정확한 오프라인 선행 은행을 가리킵니다. 선택적 `baseline.offlinePredecessor`의 artifactSha256·manifestSha256·ledgerSha256·roundId로 둘을 명확히 구분합니다. 존재하지 않는 오프라인 커밋, 원격에 없는 활성 은행, 가짜 공개 상태를 만들지 않습니다
4. 전체 원격/오프라인 확대·편집 종결 대장 원문과 모든 관련 은행을 기존 캠페인 검증기에 넣습니다. 검증된 오프라인 선행자를 담은 `offlineBases` Map은 명시적 로컬 전용 검증 문맥이며 공개 증거가 아닙니다. 전체 이력의 목표/계보 중복·한 번뿐인 근거 기반 재개방·최대 3회/계보 6회·다섯 gate·회차 일정/중복/판정 마감/종결/동결을 확인합니다. 이전 문항/선택지/출처/시드와 immutable 버전이 바뀌지 않았는지, 누적 새 문항이 정확한 accepted 집합과 일치하는지, 해설 등 발행 품질을 통과하는지도 검사합니다. `validateDeliveryChain` 통과나 해시만으로 전체 검증을 대신하지 않습니다
5. 원래 종결 대장을 verified로 고치거나 검사용 복제본의 공개 수를 부풀려 검사를 통과시키지 않습니다. `publication.status`는 not_attempted/blocked/committed_unverified 중 실제 증거에 맞추고 미확인 시각 null, 새 공개 수 0, accepted 후보의 publishedBankVersion null을 유지합니다. 오프라인 채택량은 원격 공개 coverage나 모의시험 자격으로 세지 않습니다. 다운로드로 후보 판정·횟수·내용 revision을 바꾸지 않습니다

**추후 최신 사슬 동기화:** 허용된 정상 실행에서 전체 선행 사슬을 오래된 순서로 검증하되, 각 중간 은행을 따로 공개하는 대기를 반복하지 않습니다. 최신 검증 누적본과 모든 원래 종결 대장·불변 은행 버전·전달 기록을 함께 보존하여 새로 확인한 원격 head 위에 반영할 계획을 만듭니다. `assessGitSyncPlan`에 실제 원격 ancestry와 정확한 before/after 파일 해시를 제공하고, 원래 원격 anchor와의 계보, 허용 목록, 경로·버전 충돌, 외부 변경, ref 상태와 동결을 확인합니다. 이미 정확히 적용된 파일은 재적용하지 않습니다. 다른 바이트의 같은 불변 경로나 외부 변경을 덮어쓰지 않으며, ref 불명이 충돌할 수 있으면 Git 단계만 건너뛰고 오프라인 사슬을 보존합니다. 계획 통과는 쓰기 권한이나 배포 완료의 증거가 아닙니다. 쓰기 직전 fresh head·freeze·전체 발행 검사를 다시 하고 head가 달라지면 강제 갱신하지 않습니다.

`resolvedArtifacts`에는 실제 원격 ancestry·각 체크포인트의 보존 바이트·최신 누적본의 Pages 반영·전체 대장 검사를 확인한 항목만 입력합니다. 상한 뒤 건너뜀은 여기에 넣지 않습니다. 초기 종결 원본은 영수증의 해시 검증용으로 보관하고 실제 공개 확인 기록은 별도의 정상 절차에서 갱신합니다. 이미 ref가 적용됐으나 Pages가 미확인이면 committed_unverified와 실제 commit 증거를 보존합니다.

예전 회차의 권한 timeout 상태는 영구 유지하며, 나중 회차의 허용된 catch-up은 원래 콘텐츠 roundId와 별도의 새 executionId(예: roundId=round-006, executionId=round-007-catchup-round-006)로 기록합니다. 이전 executionId의 권한 시계와 같은 artifact의 재대조 시계를 재설정하지 않습니다. 원래 후보의 roundId·검토/판정 시각·accepted 내용은 그대로입니다. 늦은 이전 승인으로 재개하지 않습니다. 별도 허용된 실행의 새 권한 요청도 실제 알림부터 10분을 넘기면 그 실행의 Git 쓰기를 종료하며 이미 끝난 artifact 재대조를 다시 기다리지 않습니다. 변경이 없으면 기존 묶음이 같다는 상태만 알리고 중복 첨부하지 않습니다. 불필요하게 사용자에게 재시도를 반복 요구하지 않습니다. 최대 검토 횟수·정규 일정·판정 마감·마지막 날 23:00 종결·23:30 재확인과 최종 동결은 그대로이며 최종 동결 이후 오프라인 확대나 미반영 은행의 새 공개를 하지 않고 마지막 정상 공개본을 유지합니다.

## 5. 최종 동결

마감: **2026-10-17 00:00 Asia/Seoul = 2026-10-16T15:00:00Z**. 마감에 배포를 시작하지 말고 그 전에 반영 확인을 마칩니다. 10월 16일 정규 후보 판정은 23:00 KST까지 반드시 종결합니다. 정규 공개·반영 확인은 가능하면 23:20까지 마치며, 23:30 최종 작업은 이미 채택·공개 확인된 정상본의 재확인과 동결 표시만 다룹니다. 지연된 정규 작업이 최종 작업 구간으로 이어지거나 미완료 후보를 되살리지 못하게 합니다. 호스팅 지연으로 신규본을 확인하지 못하면 마지막 확인된 정상본을 동결합니다.

```sh

```

이 명령은 `data/publication-state.json`의 finalized와 `data/manifest.json`의 finalRelease를 함께 true로 표시합니다. 콘텐츠 은행 해시·버전은 바꾸지 않습니다. 그 다음 `node scripts/release-guard.mjs --verify-freeze-marker`로 마감 전 동일 해시의 동결 표시만 허용하는 검사를 실행합니다. 두 표시 파일만 저장소에 반영하고 남은 공개 작업을 종료합니다. guard는 현재시간과 persistent finalized를 모두 검사하여 늦게 도착한 누적본을 차단합니다. check-only 플래그나 시계를 조작해 우회하지 않습니다. 마감이 지났다면 현재 정상본을 유지하고 동결 사실을 보고합니다.

## 6. 오류 정정

원래 사용자 답과 당시 결과는 보존합니다. 무효 문항은 새 출제 중단+invalid 정정으로 현재 조정 분모에서 제외합니다. 동일 지문·자료·표시 보기의 명백한 키 오류만 snapshotHash로 지정된 key 정정을 사용합니다. 지문/조건/보기 변경은 새 revision이며 예전 답안에 소급 채점하지 않습니다. 정정 사유/효력시각/변경점과 당시·조정 결과를 함께 표시합니다.


### 6.1 기존 채택 정규 문항의 문안 정정 (PRD 1.9)

과거 점수를 조정하는 invalid/key 정정과 구분합니다. 선택지 단서·그럴듯하지 않은 오답 등 확인된 저작 결함을 고치되 학습 목표·정답 판단·배점을 유지할 때만 별도 편집 대장을 사용합니다.

1. `docs/corrections/`의 기존 이력과 직전 공개 확인된 accepted 판정을 확인하고 실제 결함·영향 범위를 등록합니다. 같은 결함을 새 이름으로 반복하지 않습니다. 기준 은행·직전 채택 대장·문항 revision/내용 해시·targetPaths를 연결하고 대상은 기존 published·testOnly=false 문항으로 한정합니다. 최초 선행자는 확대 채택 문항이며 후속 정정은 공개 확인된 편집 개정판을 선행자로 삼을 수 있습니다
2. `editorial-ledger.schema.json`에 맞춰 `<correctionRoundId>.json`과 `.md`를 작성합니다. `changedQuestionIds`·`changedOptionIds`·`changedPracticalChoiceIds`는 실제 변경의 정확한 허용 목록입니다. 공유 선택지의 모든 영향 문항을 포함합니다. 공개 은행 하나에는 확대 대장 또는 편집 대장 하나만 적용합니다
3. 안정 questionId·optionId/choice id·templateId·learningGoalRevision·정답 역할/집합·배점을 유지합니다. 문항 revision은 시작한 검토 cycle마다 1 올립니다. 필기 option·실기 choice는 첫 cycle의 기준본, 이후 직전 cycle의 원문과 비교하여 revision 외 내용이 바뀐 cycle마다 정확히 1 올리고, 바뀌지 않으면 유지합니다. 최종 선택지 revision을 기준본+1로 고정하지 않으며 전후 해시·개정판을 기록합니다. 문항 추가/삭제·시드 변경·기존 출처 레코드 변경은 허용하지 않습니다. 새 1차 출처는 실제 확인한 근거와 함께 추가할 수 있습니다. stem·notes·part prompt·보기 instruction은 필요한 문안 정리만 허용하며 조건·범위·지식 의미는 동등해야 합니다. 자료 내용·코드·참고 답안·루브릭·정답 판단은 바꾸지 않습니다
4. 같은 직전 공개 확인된 accepted 문항의 ID·revision·내용 해시에 대한 모든 대장/ID의 시작 검토를 합쳐 최대 3회, 시작 시 정한 최대 4시간·다음 예정 회차·동결·마지막 날 23:00 마감을 적용합니다. 실패·중단을 삭제하거나 새 대장·issueId·결함명으로 리셋하지 않습니다. 원 채택/앞선 정정의 키 노출 검토자를 제외한 새 맹검과 모든 다섯 gate를 매 수정본에 다시 수행합니다. 매 cycle의 실제 question/연결 options를 `docs/corrections/evidence/<correctionRoundId>-cycle-<cycle>.json`에 불변 보관하고 대장의 reviewPackagePath·reviewPackageSha256로 연결합니다. 이 원문에서 contentSha256·blindPackageSha256·componentStates를 다시 계산해 검토별 변경과 revision을 확인하며 다른 바이트로 통과 결과를 재사용하지 않습니다. 공개 revision 1 이후 revision 2가 revise, revision 3이 accepted라면 같은 선행자에 대한 검토 2회이며 중간 실패를 없애거나 횟수를 초기화하지 않습니다
5. 새/변경 문항의 엄격한 해설 저작 검사와 앱·저장 회귀를 통과한 수정만 새 bankVersion으로 준비합니다. 한정어를 지운 결과 다른 선택지도 참이 되는 반례를 반드시 확인합니다. 3회 미통과·판정 마감·해소 불가능 사유는 rejected로 끝내며 같은 rejected 선행자는 이번 campaign에서 다시 열지 않습니다. 한 선행자에 성공 공개된 후속 개정판은 하나만 허용하며 분기·오래된 선행자 재사용을 막습니다. 실제 성공 공개 뒤 새 결함은 그 새 개정판·해시를 선행자로 연결한 별도 유한 검토가 가능합니다. 신규 후보의 1회 재개방 정책으로 우회하지 않습니다
6. 다음 확대 회차에 최신 정정 대장·보고서·활성 은행과 기존 확대의 미완료 범위·공유 선택지 공백을 함께 전달합니다. 정정 이력을 지우거나 마지막 확대 은행을 다시 기준으로 삼지 않습니다. `newRegular: 0`, 수정 채택 수와 실제 공개 확인된 수정 수를 분리합니다. 누적 고유 문항 수·모의시험 가능 여부는 실제 은행을 재계산하되 문안 정정으로 증가시키지 않습니다. 이전 불변 릴리스·종결 대장·저장 스냅샷·답안·점수·순서는 보존하고 새 세션에만 수정본을 적용합니다. 실제 호스팅 확인 전에는 수정 공개 완료로 보고하지 않습니다

편집 대장 검사는 `node scripts/validate-round.mjs docs/corrections/<correctionRoundId>.json --release` 경로로 수행합니다. 후보 은행은 먼저 기존 `validate-bank.mjs`·`build.mjs`의 명시적 후보 경로로 검사하고, 현재 은행의 인자 없는 build/check와 릴리스 gate에서도 편집 이력·변경 허용 목록·엄격한 해설 검사를 확인합니다. 기존 확대 대장 검사 경로는 유지합니다.

이 절은 실행 계약이며, 실제 검사 결과·공개 여부는 해당 정정 대장과 검증 보고서에서 확인합니다. 구조·해시 검사만으로 같은 결함의 별칭이나 선택지 의미를 자동 판별했다고 주장하지 않습니다. 마감 후에는 기존 별도 요청/승인 규칙을 따릅니다.

`prepareReleaseBackupContinuation`은 검토된 009 부트스트랩 뒤의 **정상 `release_backup` 두 ZIP**만 처리한다. 새 Git 요청·권한 timeout·공개 확인·unknown 해결을 만들지 않는다. 현재의 좁은 경로는 원래 실제 원격 anchor를 유지하며, 다른 원격 head를 임의로 승인하지 않는다. 다른 head/공개 상태로 전환하려면 별도 실제 ancestry·공개 확인 절차를 먼저 수행한다.

1. 현재 회차를 정확한 전달 선행자에서 저작·종결하고 전체 캠페인/발행 검사를 수행한다. `writeReleaseDeliveryPair`에는 실제 확인한 원격 기준 트리·현재 회차 시작 이후 확인한 `baseVerifiedAt`·정확한 검토 inventory를 제공한다. 기본 원격 coverage와 로컬 accepted 누적량을 구분한다. Git 쓰기 직전의 fresh head/양쪽 동결/권한 검사는 별도이며, 포장 manifest의 시각만으로 실제 원격 관찰을 증명하지 않는다

## 누적 공개 증거의 append-only 후속 등록

실제 payload 커밋·parent/tree·해당 커밋의 Pages 성공·live 파일 해시를 확인한 뒤에만 새 `docs/publications/` 이벤트와 `PUBLICATION_SYNCHRONIZATIONS`의 다음 고정 해시를 독립 검토하여 추가한다. 새 이벤트는 직전 증거 SHA-256, 원래 각 회차의 대장/은행, 정확한 원래 전달 proof 경로/해시와 실제 전달·검증 시각, 원격 전체 inventory를 연결한다. 기존 proof·종결 대장·은행·전달 manifest·원래 unknown/not_attempted·009 원격 anchor는 그대로 둔다. 자기 자신을 포함하지 않는 실제 payload와 뒤따르는 증거 지원 커밋을 구분한다.

정상 현재 `loadRoundContext`는 등록된 공개 proof 및 필요한 원본 전달 의존성을 자체 허용 목록과 실제 파일에서 확인한다. proof 누락을 과거 importer 이름, Boolean, Map 또는 임의 감사 시각으로 허용하지 않는다. 새 회차는 확인 시각 뒤 최신 공개 은행을 사용하며 현재 양쪽 동결·cutoff·fresh 원격 head/ancestry를 다시 확인한다.

이미 동결된 전체본은 새 증거 파일을 소급 삽입하지 않는다. 별도 읽기 전용 `auditHistoricalRelease(root)`는 검토된 공개 이벤트가 연결한 정확한 원래 전달 proof에서 전체 파일 inventory와 `deltaManifest.preparedAt`을 얻는다. 후보의 전체 허용 목록 및 모든 파일 바이트/크기/해시가 그 원본과 같을 때만 그 기록된 경계에서 역사적 발행 검사를 수행한다. 반환은 `exact_historical_delivery_audit`이며 `currentReleaseClearance:false`, `canStartNewContent:false`다. 현재 공개·새 콘텐츠·Git 재시도 승인이 아니다. 변경분을 검사할 때는 확인된 원래 공개 anchor에 적용하여 같은 정확한 전체본을 먼저 복원한다.

전달 체크포인트 내부의 중간 은행 검사도 각 원본 `preparedAt`까지 실제 시작된 대장/정정과 그때 이미 적격한 선행 증거만 사용한다. 미래 공개 proof의 고정 해시는 확인하지만 기준으로 활성화하지 않는다. 그 뒤 별도의 전체 현재 캠페인/발행 검사를 수행하므로 과거 검사가 현재 최신 은행·동결·원래 전체 의존성 검사를 대체하지 못한다.

## Git 전송: 개별 blob과 SHA-only tree

공개 전송의 기본 경로는 검토된 파일별 `create_blob`과 SHA-only `create_tree`다. 정확한 바이트 길이·SHA-256·Git blob SHA를 먼저 계산하고, 원격에서 존재와 동일성을 확인한 blob은 재사용한다. 필요한 blob만 별도로 생성하며 성공 응답의 SHA를 계산값과 대조한다. 모든 blob이 확인된 뒤 tree에는 `path`, `mode:100644`, `type:blob`, `sha`만 담는다. 큰 파일 본문을 tree의 `content`에 섞지 않는다. 내용 편집·줄바꿈 변환·redaction으로 전송 문제를 피하지 않는다.

누적010과 누적017 공개 작업에서 tree 무응답 정체가 각각 보고되었다. 원래010 요청의 정확한 입력은 확보하지 못했으므로 동일 payload였다고 단정하지 않는다. 정확한 입력을 재구성한 2026-10-05 누적017 요청은 67개 변경 경로 중 58개 inline 파일(3,845,437바이트)과 은행 SHA 참조9개를 담았고 compact JSON은 4,027,001바이트였다. 이 요청은 응답 없이 정체되었다. 235바이트 SHA-only canary는 9.872초에 기존 기준 tree를 반환했다. 이후 58개 blob을 개별 생성하고 확인된 은행 blob 9개를 재사용한 8,340바이트 SHA-only target 요청은 8.026초에 성공했다. 결과 전체 tree는 검토한 178파일 tree `cb46eebf28c239a69dae310da01eeeb79027aa7a`와 같았다. 4,366,904바이트 은행의 개별 create_blob은 성공했으므로 일반적인 4MB 전송 상한으로 설명할 수 없다. 이는 관측된 전송 방식의 개선이며 backend의 정확한 원인, POST 크기 제한 또는 보편적인 실패 임계값을 증명하지 않는다. Canary나 재제출은 자동 운영 단계가 아니다.

`scripts/sha-only-tree.mjs`의 `prepareShaOnlyTreeRequest`는 검토 inventory의 현재 실제 바이트·경로·해시를 다시 검사하여 SHA-only 요청을 만들고 `validateShaOnlyTreeRequest`는 inline content, 미확인 blob SHA, 추가 필드, 중복·위험 경로·삭제를 거부한다. 이 helper의 반환값은 GitHub REST 본문 형태 `{base_tree, tree}`다. 현재 연결된 `create_tree` 도구에는 저장소를 별도로 확인한 후 `repository_full_name`, `base_tree_sha: request.base_tree`, `tree_elements: request.tree`로 정확히 대응시킨다. connector 인자 이름이 바뀌면 실제 도구 schema를 다시 확인하며 반환값을 그대로 전송하지 않는다. 이 읽기 전용 보조 도구는 전달된 remote 확인값의 진실성, Git 권한, 현재 head, ancestry, 동결 또는 공개 성공을 대신 검증하지 않으며 `publicationClearance:false`다. 삭제가 필요한 작업은 별도 승인·검토 경로를 따른다.

공개 직전 60초 이내에 다시 확인한 원격 head/tree와 검토 기준이 같은지, 외부 변경·ancestry·경로/버전 충돌이 없는지, 로컬/원격의 두 동결 표시와 실제 현재 시각·최종 cutoff·전체 검사 결과를 확인한다. 은행·manifest·보존 기록은 하나의 검토 tree/commit에 묶고 기대한 단일 parent를 확인한 후 `force:false`로 main을 한 번 원자 갱신한다. commit/ref 성공만으로 실제 공개로 세지 않고 정확한 head의 Pages 성공과 live 길이/해시를 다시 확인한다.

권한 승인 대기와 도구 실행 중/무응답을 구별한다. 실제 권한 요청 알림이 없으면 권한 대기라고 추정하거나 그 10분 시계를 만들어 내지 않는다. 실행 무응답의 원인도 권한 문제라고 단정하지 않는다. 이미 제출된 불명 쓰기는 기존 최초 지속 기록·유한 재대조 기한으로 종료하고 unknown을 실패·미변경으로 바꾸지 않는다. 인코딩·요청 크기·tool을 바꾼 맹목적 재시도는 금지한다. SHA-only 기본값은 이전 unknown 쓰기의 재시도 권한, 거부 우회, 늦은 승인 후 재개 또는 새로운 권한을 부여하지 않는다. 별도 명시 승인이 필요한 예외는 기존 좁은 규칙과 독립 검토를 그대로 따른다. 진행 중 무응답 작업의 ref 후속 단계를 실행하거나 같은 요청을 겹쳐 제출하지 않는다.

## 독립 원격 기준의 후속 오프라인 전달 사슬

기존 `offline-chain.json`과 고정009 정상 백업 사슬은 역사적 원문 그대로 보존한다. 이후 별도로 검증한 최신 공개 기준에서 실제 권한 만료가 생기면 새 사슬의 첫 전달로 등록하며, 이전009의 원격 기준·timeout·unknown origin에 이어 붙이지 않는다. 새 사슬은 `scripts/offline-chain-continuation.mjs`와 별도의 append-only `docs/deliveries/offline-chain-trust.json`을 사용한다. 등록은 round 번호 특례가 아니라 독립 검토한 원격 commit·manifest·은행·전체 inventory와 두 ZIP·원래 종결 대장·native 첨부 증거의 정확한 해시를 기준으로 한다.

`prepareIndependentOfflineContinuation`은 실제 두 ZIP과 원래 Library 저장/두 native 첨부 수락 영수증을 검사하고 공개 가능한 제안 proof만 반환한다. 제안·prepared·실패·한 파일 수락은 전달 증거가 아니다. 외부 서비스의 원래 결과를 독립 검토한 후 새 작업본에만 proof와 registry pin을 추가한다. 이미 전달한 source ZIP은 수정하지 않으며, proof의 실제 검증 완료 이전에는 다음 회차를 시작하지 않는다. 비공개 서비스·메시지 식별자는 해시로만 연결한다.

새 root의 실제 권한 만료 시각과 최초 operation 불확실성·고정 10분 기한·실제 지속 기록한 skip을 그대로 보존한다. operation 은행 hash와 전달 delta hash의 연결은 검토된 proof에 명시한다. 나중의 Git 관찰로 최초 불확실성 시계를 초기화하지 않는다. 후속 schema2 전달은 같은 원래 reconciliation 기록을 사용하며 새로운 timeout을 만들지 않는다. 각각의 current/전달본 manifest·publication-state 동결 표시가 명시적으로 false인지와 최종 cutoff를 함께 검사한다.

loader는 등록된 각 사슬을 자기 원격 anchor에서 별도로 검증한 뒤 원래006/009와 모든 새 사슬의 증거를 전체 캠페인 검사에 합친다. 누락·자기 선언 pin·혼합 ZIP·분기·다른 같은 commit inventory·은행/대장/검토 횟수 변경·오래된 선행자·중복 목표·후기 proof의 소급 적용을 거부한다. 최신 실제 공개 기준과 최신 전달 누적 선행자의 순서를 기존 전체 검증기로 대조하며 공개 수는0, 원래 unknown은unknown으로 남긴다. 이 로컬 검사는 Git 쓰기·권한 요청·배포 권한을 부여하지 않는다.


## 첫 발행 전 안전 격리 운영

각 후보 개정판의 독립 문안 gate에서 question.explanation 자체가 정답을 도출하는 실제 규칙·계산·결과를 제공하는지 먼저 확인한다. 단순 목표·구별 대상의 이름만 적고 필요한 풀이를 정답 선택지나 part 해설에만 두지 않는다. 실제 관계를 설명하는 간결한 대조는 허용하며 선택지별 이유 전체를 중복하지 않는다. 아래 격리는 이 검토를 미루는 절차가 아니라 최종 안전 검사이며 원래 검토 횟수·마감을 바꾸지 않는다.

1. accepted 원문에서 실제 결함이 확인되면 해당 내용의 통합을 멈춘다. 원 후보·저작 패킷·채택 검토·clarification을 불변 보존하고 판정·키·횟수를 고치지 않는다. 미종결 후보는 원래 3회/마감 안에서 별도로 종결한다
2. 새 문항과 전용 선택지가 이전 모든 은행·공개/전달 proof·다운로드에 없고 다른 후보나 기존 선택지와 겹치지 않는지 독립 확인한다. 현재 작업본과 마지막 전달본의 두 freeze marker, 전체 역사 inventory와 원문을 실제 대조한다. 모호하거나 이미 전달/공개된 내용이면 이 경로를 쓰지 않는다
3. `docs/quarantines/<auditId>.json`에 필요한 identity/hash/짧은 결함 이유만 정리한다. private author/blind/raw review 로그는 공개하지 않는다. 별도 공개 QA가 원문과 canonical candidate/content/fingerprint를 직접 재계산하고 첫 발행 조건·비공유성·전체 역사 보존을 확인한 후 exact-byte 감사와 append-only trust pin을 승인한다. 자신의 Boolean이나 hash를 승인으로 쓰지 않는다
4. 원 ledger의 accepted/rejected·cycle·reason·revision을 유지한다. 검증된 quarantineDispositions의 eligible 집합만 새 은행에 넣고 해당 전용 options만 선별한다. 역사적 accepted/격리/eligible/실제 전달/실제 공개 수를 각각 보고한다. accepted 목표 예약과 이전 은행·시드는 모두 유지한다
5. 일반/오프라인 전체 campaign·release·default/explicit build·packaging 검사를 통과하고, 누락·변조·미래 증거·다른 target·alias·shared-option·동결·cutoff·과거 published 선행자 오용의 음성 검사를 실행한다. exact-byte 독립 seal 후에만 통합한다. Git/Pages·Library/native 전달 권한과 검증은 별도로 유지한다
6. 원 전달 archive를 재작성하지 않는다. 그 당시의 읽기 전용 감사는 미래 격리 증거 없이 검증할 수 있어야 하며 현재 release clearance로 재사용하지 않는다. 격리된 목표의 수정/재개방/취소/다음 회차 이름 변경은 허용하지 않는다


## 증거 소실 사고의 예약 전용 종료

전체 검토 증거·원 보고서·전달 산출물을 잃은 미전달 종결 회차는 실제 저작 결함에 대한 quarantine으로 바꾸지 않는다. `docs/release-blocks/trust.json`의 독립 검토한 append-only pin과 별도 이벤트로 full 원 대장 바이트·모든 후보 이력·시작한 모든 개정판의 내용 지문·전용 선택지·은행 버전을 예약한다. 새 내용 판정·cycle·재검토·공개·전달 proof를 만들거나 원 대장을 다시 쓰지 않는다.

사고 보고서는 날짜가 명확한 `docs/incidents/`의 별도 파일이다. 정확한 원 대장·이벤트·사고 문서가 검증된 경우에만 해당 원 Markdown 보고서 부재를 `reservation_only_missing_original_report`로 만족한다. 이는 소실 보고서의 복구나 원 pass 요약에 대한 현재 실행 증거가 아니다. 다른 누락 보고서에는 적용하지 않는다.

`evidence-loss-block.mjs`는 기본/명시 은행, 전체 이력·baseline, outgoing 파일/ZIP와 전달·공개·후속 기준 proof에서 차단을 검사한다. 경로 변경·문항/선택지 이름 변경·호출자 Boolean/제외 목록·registry/event/대장 누락으로 해제되지 않는다. 원래 복구 은행은 비공개 증거이며 공개 불변 은행이나 ZIP에 넣지 않는다. active 은행은 마지막 실제 전달 검증본을 유지한다.

후속 정규 회차는 기존14.3에 따라 최신 실제 전달 검증 은행에서 독립 목표를 선정할 수 있다. 채택 목표를 재검토해 증거 소실을 치유하거나 이름만 바꿔 재사용하지 않는다. 탈락 목표의 기존 새 1차 근거·campaign당1회 재개방 조건은 그대로이며 이 이벤트 자체는 근거·권한이 아니다. 모든 실제 새 후보에는 전체 재개방·일정·마감·동결·현재 시각·발행 검사를 적용한다. 원 탈락 원문·별칭과 예약된 전용 선택지를 재생하지 않는다. 사고 전 정확한 역사 archive의 읽기 전용 검증은 미래 이벤트를 요구하지 않으며 현재 발행 권한을 제공하지 않는다.


## 독립 오프라인 사슬의 공개 동기화 계약

별도 공개 이벤트가 독립 전달 checkpoint를 참조할 때 `delivered_independent_offline_checkpoint`의 원문 SHA, reviewed trust의 path/round/chain/anchor/predecessor와 정확한 embedded receipt SHA를 함께 검사한다. 전체 사슬의 실제 원래 영수증·manifest 검증 뒤에만 소속을 확인한다. 서로 다른 원격 anchor의 사슬을 연결하거나 caller Boolean/Map을 외부 사실 대신 사용하지 않는다. 실제 payload의 원격 전체 inventory에는 자기 전달 checkpoint·trust prefix와 모든 불변 대장·은행·원래 공개 증거·격리·발행 차단·사고 기록을 보존한다.

새 independent source는 기존 provenance 필드와 함께 `receiptSha256`, `accepted`, `quarantined`, `eligible`, `newlyPublicRegular`를 명시한다. accepted는 역사적 채택 전체이며 eligible은 검증된 격리 disposition에서만 도출한다. round-022는 accepted31·quarantined19·eligible12이고 receipt의 acceptedGoalIds31을 보존한다. 실제 bank와 정확한 baseline의 새 questionId 집합은 eligible 후보 집합과 같아야 한다. 전체 정규·필기·실기·testOnly·과목별 수와 anchor 대비 새 공개 수는 실제 최종 bank에서 다시 계산한다. 원래 두 공개 이벤트에는 새 필드를 소급 추가하지 않는다.

## 검증 실행의 통합과 정확한 증거 재사용 (validation-efficiency-001)

검사의 목적은 고유한 의미·안전 계약의 확인이며 실행 횟수 자체를 늘리는 것이 아니다. 같은 정확한 입력과 같은 계약을 연속 명령에서 반복 계산한 횟수를 독립 검토 수나 품질 지표로 보고하지 않는다. 테스트 수는 실행 대조용으로만 남기며, 이름·문장이 비슷하거나 오래 걸린다는 이유만으로 테스트 사례·불변 조건을 삭제하지 않는다.

- 모든 변경 문항의 정확한 개정판에는 독립 맹검 풀이, 1차 출처·범위·권리, 정답 유일성·반례, 문안·접근성, 구조·엄격한 해설 검사가 필요하다. 공유 선택지·출처 변경의 영향 문항도 다시 검토한다. 후보 cycle·계보·일정·실패·불변 이력·격리·증거 소실 예약은 그대로 보존한다
- 릴리스마다 전체 campaign·불변 과거 파일·활성 은행의 의미 검증을 충족한다. 섞기·정답 집합·채점·저장 순서·스냅샷·백업·시간·AI 경계·접근성 동작의 고유 회귀를 보존한다. 동일 입력의 중복 실행과 서로 다른 의미 계약을 구별한다
- `npm run release:validate`는 기존 전체 `validate-round --release` 호출과 소스 검사를 각각 한 번 실행하고 시작/끝에 실제 시각과 두 영구 동결 표시를 확인한다. 기존 `check`, 직접 `validate-round --release`, `release:check -- --check-only`를 같은 스냅샷에서 연속 실행하던 묶음 대신 쓸 수 있다. 기존 단독 명령은 완전한 검사를 유지하며 새 명령은 `npm test`, build, archive 검사 또는 실제 공개를 수행했다고 뜻하지 않는다. 전체 이력 loader 안의 반복 검증은 이 단계에서 그대로 둔다
- 새 명령은 입력 proof·skip flag·사용자 시각을 받지 않고 실행 시작/끝의 전체 경로·파일 바이트·runtime 정체성을 비교한다. `.git` 관리 영역 외 숨김 파일·의존성·빈 폴더도 비교하며 symlink는 거부한다. 외부 수정자가 없는 별도 고정 작업본에서 실행하고 로그·상태 파일은 작업본 밖에 쓴다. 시작/끝의 일치는 중간에 다른 프로세스가 변경하지 않았다는 증명을 대신하지 않는다. 실행 중 입력이 바뀌거나 결과가 비종결이면 통과로 쓰지 않는다
- 기본/명시 경로가 같은 은행 바이트를 가리킬 때 동일 발행 검사를 반복할 필요는 없다. 다만 후보 경로의 별도 규약, 변경 은행·manifest 정합성, immutable collision 및 각 API/CLI의 동작 회귀는 유지한다. 새 명령이 명시 후보 bank 검사를 수행한 것으로 보고하지 않는다

### 동일 archive에 대한 종결 소스 증거의 재사용

이 개정 이후에는 아래 조건을 전부 독립 확인한 정확히 동일한 재구성본에서 결정적 전체 corpus의 중복 실행을 생략할 수 있다. 기존 전체 archive 실행 의무의 명시적 대체 경로이며 과거 미실시를 실행으로 바꾸지 않는다. 구현되지 않았거나 증거를 확인할 수 없는 경우 기존 전체 실행 경로를 사용한다. 새 통합 CLI 자체에는 저장 proof를 읽거나 archive 실행을 생략하는 기능이 없다.

1. 실제 실행한 명령·검사/runner 원문·전체 전이 의존성·fixture·package/lock·schema·trust pin·문서 입력과 추가/누락에 민감한 전체 경로 집합의 SHA-256/크기 inventory, Node/runtime·platform·dependency 환경, 시작/종료·exit/TAP·원본 로그가 정확히 결박된 성공 종결 증거를 보관한다. 해시 문자열·commit 이름·mtime·테스트 파일만 같거나 호출자가 만든 pass Boolean은 증거가 아니다. 원 실행과 독립 보관 기록의 일치를 확인하고 검사되지 않은 의존성은 보수적으로 전체 무효화한다
2. 전체 ZIP과 delta는 각각 별도로 안전 경로·허용 목록·privacy·중복/대소문자 충돌·CRC·크기·모든 파일 SHA를 검사한다. 전체본을 새 빈 폴더에 추출하고 delta는 실제 고정 원격 base에서 before/after로 독립 재구성한다. 두 결과 각각이 검토 소스의 전체 파일 집합 및 바이트와 같음을 확인한다. 이력·원 proof·은행·누락 파일 검사를 건너뛰지 않는다
3. 두 재구성본에서 각각 빈 폴더 시작/import/build smoke를 실제 실행하여 숨은 외부 파일·경로·환경 의존성이 없음을 확인한다. 쓰기를 하는 build는 폐기 가능한 고정 사본에서 실행하고 입력/출력 정체성을 확인한다. 서로 다른 runtime/dependency 또는 변경·누락 입력, 미종결/소실 증거에는 재사용하지 않는다
4. 보고서는 실제 수행한 archive 검사와 `소스에서 실행한 정확한 증거 재사용`을 구별하고 원 증거·inventory·runner·환경·종결 결과 해시와 적용 대상을 연결한다. 재사용한 테스트를 각 archive에서 실행한 것으로 세거나 표시하지 않는다. 실패와 미실시는 보존한다
5. 실제 작업 경계의 현재 시각·두 동결 표시·현재 eligibility·정확한 입력 정체성은 새로 확인한다. 역사적 읽기 전용 proof나 소스 성공 결과는 현재 공개 권한이 아니다. 실제 remote commit/tree와 그 commit의 Pages/live bytes 증거는 별도로 필요하다

### 종료가 확인된 로컬 검사 재개

로컬 검사와 자식 프로세스가 실제 종료됐는지 먼저 확인하고 원 command·source·로그·종결 기록을 보존한다. 실행 중이면 그 실행을 기다린다. 종료됐으나 종결 결과를 얻지 못했으면 원 시도를 `미완료/unknown`으로 보존하고 누락된 idempotent 로컬 검사만 새 attempt에 재실행할 수 있다. 잘린 로그로 exit 0을 만들어 내지 않는다. 원 Git 권한/불확실 쓰기의 10분 대기는 이 로컬 검사 재개에 적용하지 않는다. Git·Library 업로드·첨부·권한 등록 등 결과 불명 외부 쓰기에는 원래 재시도 금지·확인 정책을 그대로 적용한다.

### 독립 범위 제한 seal의 정상 전달 등록

정상 후속 recorder는 기존 archive seal과 `pass_independent_bounded_release_archive_and_evidence_review`를 같은 실제 전달 사실의 읽기 전용 view로 검사한다. 후자는 `verifiedAt`, 정확한 `sourceTree`·`sourceInventorySha256`·`sourceFiles`·`baseCommit`, `archives.delta/complete`, 재구성 root, 양쪽 실제 smoke와 원 증거 참조 및 `scope`를 보존한다. scope·잔여 제한과 원 SHA를 바꾸거나 전체 suite 통과로 승격하지 않는다. 새 회차 번호별 seal 형식을 추가하지 않고 이 공통 필드를 유지한다.

native 수락의 `nativeAcceptance`, upload helper 관측의 `helperCompletionObservedAt`, checkpoint의 source inventory는 원래 관측으로만 읽는다. 서버 savedAt 또는 다른 alias를 만들어 넣지 않는다. 별도 검토자는 원 seal의 증거·smoke 영수증·로그·두 실제 저장/첨부 결과를 인증한 뒤 기존 generic successor proof와 append-only 등록을 검토한다. 이 view만으로 등록·공개 권한은 생기지 않는다.

## 실제 전달된 정상 사슬의 누적 Pages 반영

DATA-CONTRACT의 `verified_normal_chain_publication`만 사용한다. 새 최종 회차도 먼저 두 실제 첨부 수락·독립 증거 검토·checkpoint 등록을 마친다. 과거 중단된 publisher는 재개하지 않으며 새로운 사용자 지시와 현재 작업의 권한을 별도로 확인한다. 현재 원격 head/tree·동결·cutoff·충돌을 다시 읽고, 검토된 정확한 source의 통합 검사를 한 번 실행한다. SHA-only inventory로 새 payload를 반영하고 exact-head Pages와 필수 live 경로를 대조한 뒤에만 별도 공개 event/pin을 독립 검토·등록한다. 원 receipt 해시·대장·은행·proof·trust prefix와 모든 미확정 쓰기 시각은 보존한다. 후속 지원 commit의 원격/Pages/live 확인도 별도로 마친다.
