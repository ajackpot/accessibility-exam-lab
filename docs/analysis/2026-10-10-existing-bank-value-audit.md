지문: 캐나다의 한 기관이 같은 날 접근성 계획을 큰글자 형식과 점자 형식으로 달라는 요청을 각각 받았다. 규정 제8조제3항의 두 형식별 최대 제공기간을 바르게 연결한 것을 고르시오.

남는 학습 가치: 요청한 접근 가능한 형식을 제공해야 한다는 원칙과 기관·형식별 적용 조건을 확인하는 태도는 유용하다.

근거 대조: 지정된 (a)~(d) 기관의 큰글자 15일·점자 45일이라는 키는 공식 통합본 제8조와 일치한다. 실제보다 빨리 제공해도 위법이라는 뜻은 아니며 문항은 최대 기한을 묻는다.

### 2 EAA 과도한 부담 평가 자료의 보관 기산점

지문: 전자상거래 사업자가 과도한 부담 평가 자료를 평가 작성일부터 5년 뒤에 폐기하도록 정했다. 제14조제3항에 맞는 보관기간의 기산점을 고르시오.

현재 키: 해당 서비스의 마지막 제공일

범위: s1 국가별 접근성 정책의 넓은 범위에 연결된다. 다만 정책의 대상·수용 범위보다 사업자의 세부 기록 보관 절차에 가깝다. 공식 기준에 이 기산점이 직접 열거되지는 않는다.

우려: 이미 5년이라는 기간을 준 뒤 최초 제공·작성·갱신·최종 제공·사본 요청 중 법정 기준일 하나를 외워 골라야 한다. 국내 2급 대비에서 이 특정 사건을 암기할 추가 이익은 작다. 전체 해설은 시작 사건이 다를 수 있다는 일반론이며 실제 정답 규칙은 선택지 해설에 있다.

남는 학습 가치: 과도한 부담 주장이 평가·문서화·책임을 수반한다는 원칙과 보관기간의 시작 사건을 구별하는 능력은 다른 규정에도 응용할 수 있다.

대안: 공통 핵심 풀의 제외 검토를 우선한다. 정책 학습으로 남기려면 과도한 부담을 임의 선언할 수 없는 이유와 평가 근거·대체 접근에 초점을 옮기거나 조항 요약을 준 자료 해석 문제로 바꾼다. 목표 변경 여부를 별도로 판정해야 한다.

근거 대조: 서비스를 마지막으로 제공한 때가 기산점이라는 키는 Directive (EU) 2019/882 제14조제3항의 고정 관보 원문과 일치한다.

출처: [Directive (EU) 2019/882 on accessibility requirements for products and services](https://accessibilite-produits-services.public.lu/dam-assets/lgislation/celex-32019l0882-en-txt-1.pdf) (Article 14(3); OJ L151/92, PDF 23쪽)

### 3 NVDA 점자 뷰어의 주황색 대기 단계

`r037-script-at-s5-w01` · revision 1 · 핵심 풀 제외 검토 · 신뢰도 높음

지문: NVDA 점자 뷰어에서 셀 라우팅을 시험하다가 셀 표시가 주황색인 동안 포인터를 다른 곳으로 옮겼다. 가이드가 설명하는 이 조작의 결과를 고르시오.

현재 키: 라우팅은 실행되지 않는다. 셀이 녹색이 될 때까지 포인터를 유지해야 한다.

범위: s5 보조공학 이용방식·점검 도구와 느슨하게 연결된다. NVDA 2026.1을 명시했으나 공식 기준은 특정 뷰어의 색상별 실행 단계 암기를 요구하지 않는다.

우려: 학습 성패가 점자 이용 원리보다 시각적 디버깅 뷰어의 노랑→주황→녹색 순서 기억에 달린다. 다른 보조기술이나 일반 웹 접근성 점검으로 전이할 부분은 작고, 현재 지문에는 점검해야 할 웹상의 오류도 없다. 색 이름이 텍스트로 제공되므로 문항 자체를 색에만 의존하는 접근성 위반으로 판정하지는 않는다.

남는 학습 가치: 입력 확정 전에 기다리는 방식과 우발적 조작을 막는 지연의 목적, 점자 셀 라우팅 점검은 유용할 수 있다.

대안: 공통 핵심 풀에서는 제외 검토하고 필요하면 NVDA 도구 사용 심화 자료로 유지한다. 재설계한다면 대기·실행 상태를 자료로 제공하고 실수 방지 또는 라우팅 결과의 확인 절차를 묻는다.

근거 대조: 녹색이 되기 전에 포인터를 옮기면 라우팅하지 않는다는 키는 NVDA 2026.1 공식 가이드와 일치한다. 실제 Windows/NVDA·점자 기기 실측은 하지 않았다.

출처: [NVDA 2026.1 User Guide](https://download.nvaccess.org/releases/2026.1/documentation/en/userGuide.html#BrailleViewer) (Extra Tools → Braille Viewer: Hover for cell routing; Speech Viewer: hover/focus pauses text updates)

### 4 NVDA 들여쓰기 톤의 탭 환산

`r027-policy-assistive-s5-w07` · revision 1 · 재설계 권고 · 신뢰도 중간~높음

지문: NVDA의 들여쓰기 톤으로 참고 사항의 줄 A·B·C를 각각 읽는다. 세 줄에서 들리는 톤의 음높이 관계를 고르시오.

현재 키: A와 B는 같고 C는 더 높다.

범위: s5 보조공학의 역할·이용방식에 속한다. 다만 특정 제품의 탭 1개=공백 4개 환산은 광범위한 이용방식 이해보다 한 단계 깊은 설정 세부다.

우려: 현재 선택지는 사실상 숨겨진 환산 상수 하나를 알고 A=6, B=6, C=8을 계산하는 문제다. 이 규칙을 모르면 일반 접근성 지식으로 도출할 수 없고, 다른 제품에 그대로 적용할 수도 없다.

남는 학습 가치: 시각적 들여쓰기를 소리로 전달하여 코드 구조를 인식하도록 돕는 기능 자체는 의미 있다. 탭의 시각적 폭과 보조기술의 해석이 같지 않을 수 있다는 점도 유용하다.

대안: 탭 환산 규칙을 참고 자료로 주고 소리로 들여쓰기 차이를 판별하게 하거나, 들여쓰기를 음성·톤으로 알릴 지원 기능을 선택하게 한다. 이때 기존 목표와 같다고 간주하여 문안 정정만으로 처리해서는 안 된다.

근거 대조: A와 B가 같고 C가 높다는 키와 탭 환산 규칙은 NVDA 2026.1의 Line indentation reporting에 일치한다.

출처: [NVDA 2026.1: indentation tone conversion for tabs and spaces](https://download.nvaccess.org/releases/2026.1/documentation/en/userGuide.html#DocumentFormattingSettingsLineIndentation) (Line indentation reporting)

### 5 HTML form의 과거 이름 맵

`r011-dom-form-s3-w04` · revision 1 · 재설계 권고 · 신뢰도 중간~높음

지문: 다음 보기의 코드를 읽고, 마지막 문장 실행 직후 result 배열의 값을 고르시오.

현재 키: [true, true, true]

범위: s3 HTML 서식·구현과 지정 HTML 5.2에 직접 연결된다. 형식상 무관한 주제는 아니나 현재 이름 조회를 배우는 기초 범위에서 레거시 이름 보존 알고리즘까지 묻는다.

우려: 현재 코드는 이름을 한 번 조회한 뒤 바꾸고 세 불리언 값을 예측하는 데서 끝난다. 왜 이 API 차이가 구현에서 문제가 되는지 맥락이 없어 past names map 자체의 기억 시험으로 읽히기 쉽다. 오답은 그 규칙의 반전들이며 일반적인 name 변경 지식만으로는 해결되지 않는다.

남는 학습 가치: DOM의 현재 상태, 객체 참조, 이름 기반 API의 동작을 구분하는 능력은 유용하다. 실제 폼 이름 변경 오류를 진단할 때도 도움이 될 수 있다.

대안: 컨트롤의 이름을 바꾼 뒤 옛 참조가 남는 실제 오류 상황을 제시하고, 현재 name을 기준으로 찾으려는 코드의 선택·진단으로 재구성한다. 기초 과정에서는 현재 id/name 조회와 명시적 요소 참조를 먼저 다룬다.

근거 대조: [true, true, true]는 고정 HTML 5.2의 form named getter와 HTMLFormControlsCollection.namedItem 규칙에 부합한다. 현대 브라우저 관측을 고정판 근거로 대체하지 않았다.

출처: [HTML 5.2](https://www.w3.org/TR/2017/REC-html52-20171214/sec-forms.html#past-names-map) (4.10.3 The form element: named property retrieval and past names map), [HTML 5.2](https://www.w3.org/TR/2017/REC-html52-20171214/infrastructure.html#dom-htmlformcontrolscollection-nameditem) (2.7.2.2 HTMLFormControlsCollection: namedItem algorithm)

### 6 ismap 클릭 좌표의 URL 직렬화

`r014-dom-html-s3-w05` · revision 1 · 재설계 권고 · 신뢰도 중간

지문: 다음 보기의 코드를 읽고, 지정한 위치를 클릭하여 링크를 따라갈 때 만들어지는 목적지 URL을 고르시오.

현재 키: https://example.test/locate?12,8

범위: s3 HTML 임베디드·링크와 지정 HTML 5.2의 명시적 규칙이므로 오래되거나 드물다는 이유만으로 범위 밖이라고 할 수 없다.

우려: 현재 문항은 실제 포인터가 정상 동작한다는 조건에서 ?12,8과 ?x=12&y=8 등을 골라 직렬화 형식만 확인한다. 같은 이미지 맵이 키보드·보조기술 이용자에게 어떤 경로를 제공해야 하는지 판단하지 않아, 접근성 학습으로의 전이가 제한된다.

남는 학습 가치: 클릭 위치를 서버로 보내는 이미지 맵과 폼 전송, URL의 질의·조각을 구별한다. 레거시 페이지를 읽을 때에는 쓸모가 있다.

대안: 좌표 직렬화는 설명 자료로 남기고, 시설별 목적지를 키보드로 선택할 수 있는 대체 경로와 링크 목적을 진단하는 문제로 설계한다. 단, 이는 학습 목표가 달라질 가능성이 커서 기존 accepted 문항의 편집 정정으로 몰래 바꿀 수 없다.

근거 대조: https://example.test/locate?12,8이라는 키는 HTML 5.2 a 요소의 ismap 활성화 규칙과 일치한다.

출처: [HTML 5.2: 4.5. Text-level semantics](https://www.w3.org/TR/2017/REC-html52-20171214/textlevel-semantics.html#the-a-element) (§4.5.1 The a element: activation behavior, server-side image map processing)

### 7 SMTP DATA의 점 추가 처리

`r009-web-tech-s2-w03` · revision 1 · 재설계 권고 · 신뢰도 중간

지문: SMTP DATA로 보내려는 원본 본문의 한 줄이 “.notice”로 시작한다. 점 투명성 처리에서 이 줄의 맨 앞에 적용할 변환을 고르시오.

현재 키: 첫 점 앞에 점 하나를 더 붙여 보낸다.

범위: s2 인터넷 응용 서비스 중 이메일에 연결되지만 공식 평가내용은 정의·기본 개념 이해다. SMTP 전송 구현의 줄 단위 이스케이프 절차는 기본 서비스 이해보다 깊다.

우려: 현재 모든 답 후보는 점을 없애거나 추가하거나 공백·백슬래시를 넣는 변환이다. 처리의 목적을 추론하는 문제가 아니라 특정 SMTP wire-format 변환을 기억해야 한다. 학습 맥락을 보강할 여지가 크다.

남는 학습 가치: 종료 표식과 실제 데이터가 충돌할 때 가역적인 이스케이프를 사용한다는 생각은 다른 형식·프로토콜에도 전이된다. 그래서 드문 프로토콜 사실이라는 이유만으로 무가치하다고 보지 않는다.

대안: 종료 표식과 점 추가·제거 규칙을 자료로 제공한 다음 원문 복원이나 데이터 손실을 진단하게 한다. 핵심 서비스 역할을 대신할 만큼 높은 우선순위는 부여하지 않는다.

근거 대조: 줄 시작에 점 하나를 추가한다는 키는 RFC 5321 §4.5.2와 일치한다. 원문 줄 끝에 본문이 있어도 점 추가가 필요하다는 조건도 맞다.

출처: [RFC 5321: Simple Mail Transfer Protocol](https://www.rfc-editor.org/rfc/rfc5321.txt) (4.5.2 Transparency)

출처: [ECMAScript 2015 Language Specification](https://262.ecma-international.org/6.0/#sec-string.prototype.codepointat)

## 확인 범위

지정 원문을 재확인한 선정 12개에서 새 정답 키 오류는 확인하지 않았다. HTML 5.2의 큰 Forms 문서는 웹 파서 크기 제한 뒤 같은 공식 URL의 직접 읽기 전용 취득으로 확인했다. 캐나다 공식 페이지는 current to 2026-09-21 표시까지 대조했다. 실제 Windows/NVDA·점자 기기 실측과 전체 은행의 정답·문안 재검증은 하지 않았다.

`audit.json`에는 선정 문항의 정확한 공개 내용, 항목별 판단, 정답·출처, 정규화 JSON 묶음 해시와 취득 자료 해시가 있다. `inventory.json`에는 전체 목록과 검토 깊이를 구별했다. 두 파일의 공개용 정보는 활성 은행과 공식 출처에 한정한다.
